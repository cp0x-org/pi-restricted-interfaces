# How to add a new protocol

Everything is done in one file, `monitor/data/interfaces.json`; the rest is generated by a command.

## 1. Collect the facts (15–30 minutes per protocol)

- **Official interface**: the exact URL of the app (not the landing page).
- **Frontend code**: whether there is a public repository on GitHub. Check: `git ls-remote https://github.com/<org>/<repo>`.
- **Terms of Service**: link, revision date, list of prohibited countries, restrictions for US persons, the VPN clause.
- **Documentation**: "eligibility", "restricted jurisdictions" and "compliance" pages, mentions of KYC and wallet screening (TRM, Chainalysis and the like).
- **Chains**: the EVM chains the official app works on.
- Keep a link as evidence for every statement.

## 2. Add the entry

Copy the template to the end of the `interfaces` array (before the closing `]`) and fill it in:

```json
{
  "id": "myprotocol",
  "name": "My Protocol",
  "description": "My Protocol is a lending market on Ethereum where users supply assets to earn interest and borrow against collateral. (80–600 characters, one paragraph in English)",
  "description_zh": "My Protocol 是以太坊上的借贷市场，用户存入资产赚取利息，并以抵押品借款。（可选，20–600 字）",
  "category": "Lending",
  "chains": "Ethereum, Arbitrum",
  "networks": ["Ethereum", "Arbitrum"],
  "url": "https://app.myprotocol.xyz",
  "frontend_repo": null,
  "repo_state": "closed",
  "repo_status": "closed",
  "repo_last_commit": null,
  "geo_site": { "s": "tos_only", "countries": [], "close_only": [], "method": "How the site block is implemented" },
  "geo_feature": { "s": "unknown", "countries": [], "scope": "" },
  "vpn": { "s": "unknown", "note": "" },
  "screening": { "s": "unknown", "provider": "", "layer": null, "fail": null, "fail_note": "" },
  "asset_filter": "",
  "tos": {
    "url": "https://myprotocol.xyz/terms",
    "updated": "2026-01-01",
    "us": "yes",
    "us_scope": "",
    "restricted": "The list of countries in your own words",
    "restricted_codes": ["US", "RU", "IR", "KP", "UA-Crimea"]
  },
  "notes": "How the restrictions work: which services and configs are involved, the state of the code. Facts only, no advice about forks.",
  "live": [],
  "geo_endpoints": [],
  "evidence": ["https://myprotocol.xyz/terms", "https://docs.myprotocol.xyz/eligibility"],
  "confidence": "medium",
  "alternatives": []
}
```

Cheat sheet of the values:

| Field | Values |
|---|---|
| `s` (status of any mechanism) | `yes` confirmed by code, a live check or documentation · `reported` press/users · `tos_only` only in the terms · `optional` in the code, off · `no` checked, none · `unknown` not checked |
| countries | ISO codes (`US`, `GB`, `DE`) or the regions `UA-Crimea`, `UA-DPR`, `UA-LPR`, `UA-Kherson`, `UA-Zaporizhzhia`, `US-NY`, `CA-ON`, `CA-BC`, `CA-AB`, `CA-QC`, `GE-Abkhazia`, `GE-SouthOssetia`, `CY-North` |
| `layer` (where the check actually runs) | `edge` (the CDN/hosting refuses by country) · `frontend` (code in the browser decides, including reading an on-chain oracle from the page) · `api` (the server refuses: a compliance endpoint, indexer, orderbook, quote API) · `contract` (the smart contract itself rejects the address: blacklist, allowlist, memberlist) · `null`. With several checks give the deepest one: `contract` → `api` → `frontend` |
| `repo_state` | `open` · `open_stale` · `closed` · `private_now` · `archived` · `none_found` (if `closed`, then `frontend_repo: null`) |
| `tos.us` | `yes` US persons are prohibited · `no` · `partial` (describe it in `us_scope`) · `unknown` |
| `confidence` | `high` · `medium` · `low` |

Optional fields:
- `"referral_url": "https://app.myprotocol.xyz/?ref=CP0X"`: where the official-app link goes when it differs from `url` (a cp0x referral link); the link text, search and probes keep `url`.
- `"kyc": { "s": "yes", "layer": "contract", "scope": "what KYC gates" }`: KYC or a wallet allowlist (counts as one restriction).
- `"alternatives": [{ "name": "myprotocol.cp0x.com", "url": "https://myprotocol.cp0x.com" }]`: if pi.cp0x.com has a permissionless version (the row moves up).
- Protocol versions: see the section below.

The rating is computed automatically from the number of restrictions: each blocked country (site, trading or features, status `yes` or `reported`) plus one each for a feature restriction, screening, VPN detection and KYC. Bans that exist only in the Terms are not counted. A — 0 (no restrictions), B — 1–5, C — 6–20, D — more than 20, n/a — nothing determined. The category group and the chain tags are computed too; do not write them.

### If a protocol has several versions

Each version with its own official interface is a separate entry (like `aave` and `aave-pro`, `notional` and `notional-v3`).

```json
"version": "V3",
"family": "notional",
"lifecycle": "legacy",
"lifecycle_note": "Being wound down after the November 2025 exploit; the app moved to v3.notional.finance."
```

- `version`: the label after the name: "Notional" + "V3" = "Notional V3".
- `aka`: a second name: a former one (`ex-Maker`), a parent brand (`0x`) or a product (`Aave Pro`); on the site it is grey next to the name, in page titles and the report it is in parentheses. Do not put the second name into `name` or `version`.
- `family`: the shared id of all versions of one protocol; a version's page gets links to the others.
- `lifecycle`: `current` (the default, can be omitted), `legacy` (the protocol itself is retiring the version: a deprecation banner, a `v2.`/`v3.` subdomain, a shutdown announcement; the row moves down with a mark), `defunct` (the official interface does not work; not shown on the site).
- `lifecycle_note` is required for `legacy` and `defunct`: the reason and a date or a source.

## 3. Build and check

```bash
pnpm monitor:build    # validates the schema; on an error it names the id and the field
pnpm build            # builds the site (+ the /monitor/<id> and /zh/monitor/<id> pages, sitemap)
pnpm start            # open http://localhost:3000/monitor/<id> and /zh/monitor/<id>
```

If `monitor:build` complains, fix the field it named and run it again.

## 3a. Add checks in research/

Every restriction that counts towards the rating (and for an A rating at least one `no` or `tos_only` check) has to be
reproducible by a script. Create `research/checks/<id>.json` (format and examples in `research/README.md`), then:

```bash
python3 -I research/check_docs.py --only myprotocol -v   # or check_code.py / check_bundle.py / check_api.py
python3 -I research/combine.py | grep myprotocol          # the rating and restriction count must match the site
```

## 4. Optional: a live check from other countries

```bash
set -a; source .env.probe; set +a                     # proxy credentials, see monitor/docs/probing.md
pnpm monitor:probe -- --countries US,DE,UA --only myprotocol
pnpm monitor:probe:merge -- monitor/probe/out/<file>.json
pnpm monitor:build
```

## 5. Publish

Commit `monitor/data/interfaces.json`, `src/data/interfaces.json` and `monitor/out/*`, then deploy
(`docker build .`, the domain `https://restricted.cp0x.com` is already configured).
